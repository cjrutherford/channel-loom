## Recovery contract

The admin backup API creates a standalone SQLite `VACUUM INTO` snapshot, including committed WAL transactions at its snapshot boundary. It contains library paths, channels, schedules, generated timeline state/cursors, database settings, token hashes and encrypted cloud secret blobs. The SQLite file itself is **not encrypted**: protect it as sensitive data, including settings and paths; Unix creation and staging use owner-only permissions. Cloud credentials use the existing encryption scheme; the matching `AWESOMETV_SECRET_KEY` (and any previous keys needed for rotation), or the separately protected `secrets/cloud.key`, must be preserved separately. The archive does not include that key, environment configuration, media, artwork, other files under the data directory, or external services. Securely back those up separately, with media mounted at the same absolute paths or otherwise remapped before playback. This change does not provide an encrypted bundle or key escrow.

On an isolated replacement instance, install the matching application/configuration, media mounts and key first. Place the SQLite file in its data directory's `backups/` with restricted permissions, authenticate as an admin, POST its name to `/api/v1/restore`, then stop and restart the instance. Staging copies to a temporary file, checks the format marker, required tables and SQLite integrity, and atomically publishes `restore.pending`. Startup repeats validation, checkpoints any existing destination WAL, preserves its database as `awesometv.pre-restore.<uuid>.db`, then installs the staged file. A rejected staging request leaves an existing pending restore intact; a damaged pending file blocks startup without replacing the database. Investigate and remove the damaged pending file only after preserving evidence. Do not run two servers against the same data directory. Verify health, settings, guide, credentials and playback before relying on the restored instance.

The format marker identifies this backup format, not a complete migration compatibility guarantee. SQLite integrity checking detects structural damage, not every valid logical alteration or malicious substitution. Record a SHA-256 digest through a trusted separate channel and verify it before restore; there is no built-in authenticated checksum. In particular, schema compatibility across future application versions is not established by the marker. Unexpected errors or a failed migration after replacement require operator recovery from the preserved database and separately protected files; this is not an atomic rollback of every application startup operation. Abrupt interruption can leave hidden temporary files; they are not listed as backups and may be removed after confirming no operation is running. No crash-injection, power-loss durability, permission-denial, remote filesystem, multi-process, or production recovery drill is claimed.

## Legacy unversioned import preflight

Keep the original backup and its separately stored key untouched, with a trusted digest. On a disposable, offline data directory, use a copy and the original application version and configuration that produced it. Before starting, open the copy read-only with SQLite and run `PRAGMA integrity_check`; require exactly `ok`, inspect the expected application tables, and stop if provenance or schema is uncertain. Restore via that version's documented mechanism (the previous server accepts the backup name in `backups/` via the admin restore API and applies it on restart). Do not point this test at a live data directory. Supply the original key and media mounts separately, then verify settings, channels, credentials, guide and playback. Preserve that recovered directory as another protected copy.

Only after establishing a supported upgrade path from that version, upgrade a **copy** of the recovered instance to the target version, check its migration/startup and repeat those functional checks. Create a new version-1 backup from the upgraded instance and test restoring it into a second disposable instance before relying on it. Never add the metadata marker by hand: it does not establish schema compatibility. If the original executable, matching key or a supported upgrade path is unavailable, retain the original and seek version-specific recovery; do not overwrite the only copy. This procedure is a preflight, not a tested legacy migration or a claim that every older schema upgrades successfully.

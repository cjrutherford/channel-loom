## Operational behavior and risks

- Local scan route is authenticated under `/api/v1`; manual request only. Cloud scan is explicitly started with `full` and default limit 1000; jobs can be queried/cancelled ([api.rs](../../crates/awesometv-server/src/api.rs#L1632)). No cloud periodic scheduler was found in startup callers. Wave 3’s hourly renewal worker is channel schedule renewal, not source refresh ([main.rs](../../crates/awesometv-server/src/main.rs#L100)).
- Google HTTP client has a 60-second request timeout ([google.rs](../../crates/awesometv-server/src/cloud/google.rs#L61)); local ffprobe subprocess timeout/pagination and Jellyfin timeout behavior should be verified in source-specific test slices.
- Cloud scan reports `complete`, errors and removed counts ([manager.rs](../../crates/awesometv-server/src/cloud/manager.rs#L38)). A full scan gates stale deletion on `complete && errors == 0`, but reaching the item limit exactly at the end of a page can break before following `next` without setting `complete = false` when the folder queue is empty. A partial listing can therefore be treated as complete and delete unseen records ([scan loop](../../crates/awesometv-server/src/cloud/manager.rs#L387), [deletion gate](../../crates/awesometv-server/src/cloud/manager.rs#L505)). This is a source-derived risk, not a reproduced incident. Upserts occur during scanning, so failed/cancelled scans may leave partial updates; stale deletions are individual transactions, so a later failure can leave earlier deletions applied even though the report is incomplete. The generic incomplete message can then wrongly say stale media was not reconciled. Deletion removes collection and channel items as well as media ([db.rs](../../crates/awesometv-server/src/db.rs#L2602)). Deleting a source removes its cache directory before its database transaction, which also removes associated collection and channel items ([manager.rs](../../crates/awesometv-server/src/cloud/manager.rs#L135), [db.rs](../../crates/awesometv-server/src/db.rs#L2547)); cache and database deletion are not atomic.
- Local scan interruption/deletion semantics and Jellyfin removal reconciliation are unverified, not known defects. No evidence supports automatic remote deletion propagation.
- Cloud credentials: Google OAuth client ID/secret and refresh token; source secret encryption key is generated/loaded from data directory ([secret.rs](../../crates/awesometv-server/src/cloud/secret.rs#L63), [google.rs](../../crates/awesometv-server/src/cloud/google.rs#L26)). Jellyfin needs base URL and API key. No Plex/Emby credentials can make an absent implementation supported.

## Safe verification plan and next slices

1. Scan slice: use temporary local fixture tree and disposable SQLite DB; assert add/change/remove policy and interrupted scan leaves prior inventory intact. Mock ffprobe or use generated fixtures. No production library.
2. Remote sync slice: mock HTTP server for auth expiry, pagination, duplicate IDs, deletion only after complete listing, timeout, cancellation and partial page failure; assert failed/partial scans preserve prior records. Then optional read-only real account verification with user-provided credentials and a dedicated disposable source; never mutate external files.
3. Decisions/defaults: define whether removals are immediate or grace-period, whether remote refresh is manual or scheduled, supported provider/version list, and limits/retry policy before enabling unattended sync. Current evidence supports manual cloud scan only; do not infer background refresh.

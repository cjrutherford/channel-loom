# Wave 3 renewal worker

The server starts one renewal worker after binding its listener. It scans immediately and then hourly; generated classic and block channels with persisted state and less than five days of horizon call the existing atomic append operation, which targets at least seven days. The operation rejects unowned continuations. Manual, external, and state-less legacy channels are not renewed. A mutex serializes scans; failed scans or channels retry after 1, 2, and 4 minutes, then resume hourly. Shutdown signals the worker and waits for an in-progress scan before stopping the engine.

Structured `renewal status` logs include channel ID, last success time, last error, persisted horizon, and risk (under five days); successful renewal clears the error and risk. A safe horizon observed from another writer also clears the error. Scan failures have a separate error log. Status is held in memory and emitted to logs, so in-memory history resets on restart; log retention is determined by the deployment.

Verification from the project root: `cargo test -p awesometv-server renewal::tests -- --nocapture` passed 2 tests on a real temporary SQLite database. An injected failure before renewal preserved all existing timeline row fields checked, set error/risk, and a retry appended through seven days and cleared both. Concurrent duplicate ticks produced no duplicates; reopening the database and advancing the injected clock triggered catch-up with contiguous rows. A separate test checked manual, external, and legacy exclusion. This injection tests worker failure handling, not a mid-transaction database failure; transaction rollback is covered by the existing renewal contract tests. `rustfmt --edition 2024 --config skip_children=true --check crates/awesometv-server/src/main.rs crates/awesometv-server/src/renewal.rs` passed. No live server or elapsed-hour shutdown test was run.

Integration gate update: per-channel renewal now has a 120-second deadline and each scan a 300-second deadline; timeout enters the existing retry path. Unsupported/unowned outcomes log a warning and stale status entries are pruned. The focused deadline test and isolated live API-created channel, restart, catch-up and SIGTERM evidence are recorded in `wave-3-checkpoint.md` and reproducible with `wave-3-lifecycle.py`. No elapsed-hour or in-flight transaction shutdown test was performed; status for a safe horizon does not independently validate continuation ownership.

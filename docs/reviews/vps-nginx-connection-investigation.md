## Findings

Three stalls after startup at 15:54:02–05, 15:54:07–14 and 15:54:18–23 recovered. Chromium received `net::ERR_NETWORK_CHANGED` on a playlist and segment at 15:54:19, and on a retry at 15:54:21. A local NetworkManager record shows a Docker veth interface event at 15:54:19; temporal coincidence is not proof it caused Chromium's network change. The first stalls began earlier.

One browser playlist on a reused HTTP/2 connection waited 8.59 seconds for headers ending at 15:54:05.424. The corresponding long-lived browser connection's nginx playlist record ended at 15:54:05.503 and reports 0.060 seconds total and 0.056 seconds to upstream headers. Allowing for clock uncertainty, this supports delay outside nginx's measured request handling, on the browser/public network path; it cannot locate the exact link or explain every stall. During the final interruption nginx recorded a segment with 0.045 seconds to upstream headers but 5.356 seconds total, consistent with slow downstream delivery or backpressure, not proof of which network hop caused it. Other requests did experience upstream header delays (maximum 1.336 seconds across the capture), so this is not a proof that the upstream path never contributes.

Of 180 CDP responses, 178 used reused HTTP/2 connections; two established connections. This does not support a DNS lookup per fragment. The separate-process normal DNS probes had 59/61 successes and two resolver timeouts, while pinned public had 60/61 successes and one timeout with no response bytes; local origin had 61/61 successes with maximum total 1.7 ms. These probes are separate connections and do not prove browser behavior. The publisher log was captured in the evidence directory; successful local playlist probes and ongoing publication do not rule out every publisher or media continuity issue. Across 414 ATV nginx requests, upstream header p50/p95/max was 0.040/0.124/1.336 seconds; 413 were 200 and one 499. Percentiles exclude the one missing upstream header. Historical nginx logs include upstream connect timeouts and refusals, but no ATV error was recorded during this capture. A five-minute observation cannot establish the universal cause of playback jank.

## Deployed configuration and actions

The actual `swag` container loaded `/opt/swag/config/nginx/proxy-confs/atv.subdomain.conf`; the repository version is not the deployed source of truth. It proxies HTTP to `nirvana.tail5a4a0.ts.net:8409`, resolved at load to `100.120.253.100` and routed over `tailscale0`; this upstream hop does not use TLS. Public TLS and HTTP/2 terminate at SWAG. The vhost sets upstream HTTP/1.1, `Connection ""`, `Host $host`, `keepalive 32`, buffering and request buffering off, and no enabled proxy cache. Connect timeout is 10 seconds; read/send timeouts are 3600 seconds. nginx's configured resolver is Docker DNS, but the static upstream hostname is resolved at configuration load rather than dynamically refreshed. Host and TLS settings were not changed. SWAG had zero container restarts, available memory, and low load during the audit.

A temporary HTTP-level log format and ATV-only access log captured timestamps, query-free URI, connection count, status and upstream/request timings. Both exact configuration files were backed up locally in the evidence directory and on the VPS in `/root/atv-nginx-backup-kb4k0tzS` (owner-only). nginx configuration test passed before each graceful reload. After capture the instrumentation was removed by restoring the original contents after checking there were no intervening edits; no routing or timeout fix was justified. The remote timing log remains owner-readable at `/opt/swag/config/log/nginx/atv-timing.log`; it is no longer actively written by nginx. Public HTTPS playlist returned 200 with certificate verification after restoration, and SWAG remained running with zero restarts. The backup files allow restoration of the original configuration followed by `docker exec swag nginx -t` and, only on success, `docker exec swag nginx -s reload`; verify no intervening edits first.

Further investigation should trace the browser host's route/interface changes and the public path during a reproduced stall, and repeat from an independent client. Avoid interpreting a pinned address, longer timeouts or an nginx keepalive change as a proven cure. Playback improvement has not been demonstrated.

# Wave 6 remote refresh: bounded cloud safety checkpoint

Cloud listings stage media and metadata in memory and publish them in one SQLite transaction only after a complete, error-free scan. A scan at its item limit is conservatively incomplete even when it might have ended exactly there; repeated page tokens and a 10,000-page ceiling also prevent an unbounded listing from being called complete. Failed listing attempts are retried at most three times, and Google requests use the existing 60-second timeout. Scan job failures and Google HTTP errors no longer include provider error strings, which can contain URLs or secrets. Failed scans preserve the prior successful sync timestamp. Full scans currently retain stale records, including after successful scans: atomic stale deletion and cache cleanup remain to be designed. This avoids partial deletion at the cost of retaining removed media.

Evidence: `cargo test -p awesometv-server cloud::manager::tests::mock_provider_lifecycle_conformance -- --nocapture` passed. The mock provider uses paginated folder listings and verifies normal publication, an item-limit scan preserving records and successful timestamp, and rollback after an injected SQLite update failure. This is not HTTP timeout, 401, transient retry, log-capture, cancellation, or real-account evidence. No cursor is currently persisted by this cloud scan. Google and Jellyfin have different sync contracts; Jellyfin and its caller remain unchanged and need independent recovery tests. Concurrent scans and atomic deletion also need follow-up before unattended refresh is accepted.

Integration handoff: shared bootstrap (`main.rs`) is intentionally untouched. A scheduler must be implemented and wired there to select enabled sources with enabled roots, avoid overlapping manual/scheduled jobs per source, run at six-hour intervals, and use `CloudManager::start_scan(source_id, limit, true)` with an explicitly chosen limit. It must account for failed attempts without overwriting last successful status, and be tested with a controllable clock. The current change does not implement that worker or enable scheduled refresh. Hosted provisioning and real provider verification were not attempted.

## Slice 10 HTTP and Jellyfin checkpoint

Jellyfin/Emby listings now require a consistent `TotalRecordCount`, validate each page, reject a listing over the limit, and return staged media only after the reported total is reached. Requests have a 30-second timeout, disable redirects, retry transport errors and HTTP 429/5xx up to three attempts, and return sanitized errors; 401 is not retried. `jellyfin::commit(&pool, &media)` publishes staged rows in one SQLite transaction, retaining stale rows to protect schedule references. This function is **not yet wired**: both callers in `api.rs` still write individually, so a database failure can partially publish. No Jellyfin status is maintained by these callers. A follow-up must replace both per-item loops with `jellyfin::commit` and propagate its error; do not mark an attempt successful until it commits.

Fresh local mock evidence: `cargo test -p awesometv-server jellyfin::refresh_tests -- --nocapture` passed 3 tests: retry, 401, exact limit, later-page failure, short timeout, and SQLite rollback. `cargo test -p awesometv-server cloud::google::tests::http_pages_and_auth_error_are_sanitized -- --nocapture` passed 1 test for page token and sanitized 401. Tests use loopback HTTP and in-memory SQLite, not real provider accounts. The existing cloud manager retries all listing failures, including 401, because its retry loop cannot distinguish auth from transient errors. Cloud HTTP timeout/retry/page-failure combined with SQLite no-mutation assertions remain untested; the earlier provider-level lifecycle test is not HTTP evidence. The six-hour bootstrap worker and per-source overlap exclusion remain the previously stated follow-up. No stale deletion is attempted.

## Slice 10 integration follow-up

Both Jellyfin and Emby manual endpoints now use `remote_refresh::sync_library`, which holds a per-provider exclusion lock through staging and `jellyfin::commit`; failures return a generic endpoint error. The startup worker uses the same path for configured credentials. It also starts full scans for enabled cloud sources with enabled roots through the same `CloudManager::start_scan` used by manual requests. Each scan has a 20,000-item limit; the worker uses a 30-minute deadline, six-hour successful interval, and exponential failure delay from five minutes to six hours. Shutdown signals the worker and cancels its active cloud job. Cloud job state reports incomplete scans as failed; cloud source `last_error` is updated without changing its last successful timestamp. Jellyfin/Emby scheduled outcomes are logged generically, not persisted as status records. Google 401/403 listings carry a typed authentication error and are not retried. Other listing failures receive up to three attempts with bounded delay and a 65-second per-attempt outer deadline. Stale records are retained even on successful full scans: this is a conservative safety policy, not deletion parity.

Evidence in this workspace (no real accounts): `cargo check -p awesometv-server` passed; `cargo test -p awesometv-server jellyfin::refresh_tests -- --nocapture` passed 3 tests; `cargo test -p awesometv-server cloud::google::tests::http_pages_and_auth_error_are_sanitized -- --nocapture` passed 1 test; `cargo test -p awesometv-server cloud::manager::tests::mock_provider_lifecycle_conformance -- --nocapture` passed 1 test. The latter uses a provider mock and SQLite to check a successful baseline, item-limit retention, a typed authentication failure with one attempt, a simulated later-page timeout after staged entries, recovery, transaction rollback, and exclusion of a concurrent job followed by another successful job. The HTTP 401 test is separate from that SQLite test; the timeout is injected by the mock rather than an actual HTTP timeout. Tests do not exercise the new API endpoints, the scheduled worker with a controlled clock, or cancellation during a commit. The worker's Jellyfin/Emby status is log-only, and blocking provider operations already in flight cannot be forcibly stopped; their bounded network calls can outlive a cancellation. Real provider accounts, runtime deployment, deletion reconciliation, and credential-leak log capture were not tested.

## Slice 10 local acceptance follow-up

The cloud scan now stages media and its success timestamp in one SQLite transaction. A cancellation flag and publication mutex serialize cancellation with publication: cancellation marks the job first and waits for any publication already in progress, while a staged commit checks the flag before committing. Thus a cloud scan cannot publish media or status after `cancel_scan` returns; a transaction already committing can complete before cancellation returns. The same gate covers scan failure status writes. Stale media remains deliberately retained. Google authentication and probe calls now use blocking tasks with 65-second async deadlines, as listings already did. A timed-out blocking task is **not aborted**; an arbitrary provider or probe can continue running beyond that deadline. Provider network requests have their own timeout, but this does not prove a hard lifetime bound for arbitrary implementations or OS-level work.

Local focused evidence: `cargo test -p awesometv-server remote_refresh::tests -- --nocapture` passed 1 controlled-clock test for immediate startup, six-hour success interval, exponential backoff capped at six hours, recovery scheduling and shutdown. It exercises the production scheduling loop with an injected attempt, rather than a complete configured worker with real providers. `cargo test -p awesometv-server cloud::manager::tests:: -- --nocapture` passed 4 tests, including a real loopback Google HTTP/SQLite test for baseline success, 401, socket timeout, later-page 401 after staging an item, retained last-good row and timestamp, and subsequent recovery. The provider lifecycle test also covers same-source manual job exclusion, cancellation while a blocking listing is in flight, rejection of a cancelled staged commit, SQLite rollback, and a later successful scan. The HTTP test checks that the sentinel credential is absent from persisted error text; it does not capture tracing output. No real accounts were available.

Residual: Jellyfin/Emby staging runs in a blocking thread and is discarded if the awaiting future is dropped, but cancellation can race with its asynchronous SQLite COMMIT once submitted; SQLx does not establish that a dropped COMMIT future cannot finish afterward. The cloud gate above does not cover this separate path. A complete cross-provider guarantee needs a cancellation-aware publication coordinator that waits for a submitted Jellyfin/Emby commit before shutdown returns, plus a deterministic test at that commit boundary. Cloud cancellation can likewise wait for an already-started SQLite transaction; its wait is not independently time-bounded. This is a late-publication/shutdown-latency risk, not evidence that `spawn_blocking` cancellation terminates its thread. Credential-bearing tracing capture, full configured-worker/manual endpoint integration, and real-account validation remain open.

## Integration update

The preceding Jellyfin/Emby shutdown residual is addressed for the scheduled worker: shutdown is observed during listing, and publication runs in an owned task that shutdown joins. Its cancellation check is the linearization boundary: a stop observed before admission rejects the staged rows; an admitted transaction may commit and is awaited, not rolled back by promise. The provider lock travels with the blocking listing and then publication. Dropping a manual request sets its cancellation flag, but an already admitted transaction can still finish; graceful server shutdown also drains requests. Neither SQLite transaction completion nor blocking-provider thread lifetime has a hard shutdown bound. A timed-out blocking listing can continue, but its result has no publication path and its provider lock stays held until it returns.

The current SQLite test schedules a publication and signals stop before it can execute, verifies the last-good row, and verifies a later publication; a separate lock test checks same-provider exclusion, different-provider independence and lock release. It does not force a stop during an already admitted SQLite COMMIT. `main` starts the production worker; the controlled-clock test injects attempts into its scheduling loop, not an end-to-end configured worker. Manual endpoints call the same provider locking function. Cloud loopback tests check sanitized persisted errors; a tracing sentinel was not captured. Inspection finds generic listing/probe warnings on the refresh path; other diagnostics are outside that focused proof. Real-account validation remains open.

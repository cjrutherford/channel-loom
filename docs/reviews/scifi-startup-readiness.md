## Candidate engine changes

On a publisher restart more than 10 seconds behind wall time, preserve the advertised prefix, sequence and anchor, advance the cursor to the current scheduled time, and mark the next segment as a discontinuity. No historical gap is encoded. Resume parsing permits a forward PDT gap only at an explicit discontinuity. Existing segment URLs are retained under the existing retirement policy. This policy does not repair an already running old process until integration deploy/restart. Normal in-progress publication is not retimed.

Private startup now requires at least `prebuffer_seconds` of newly published, closed playlist media, with at least one segment when set to zero. Private unpublished spool entries and retained older playlist entries no longer satisfy the watermark. The bounded wait is 45 s. Preparation horizon honors the existing 0–30 s prebuffer setting; two bounded generations remain the concurrency limit. Suggested integration candidate for channel 4: prebuffer 8 -> 12 s (three 4 s segments), retaining 24 segments and prewarm off initially. This is a proposed persisted setting, not applied. Actual segment durations and cache depth can make a requested watermark unreachable; a deadline must report failure, never claim readiness. A 12-second watermark takes at least about 12 seconds of scheduled publication on a cold start, plus any encoder delay.

Logs: `/tmp/atv-watermark-test.log`, `/tmp/atv-watermark-deadline.log`, `/tmp/atv-preparation-test.log`.

**Blocking cross-lane contract:** `playlist_for_channel` in `api.rs` returns an mtime-fresh playlist immediately and calls `ensure` in the background. It can therefore bypass the new startup watermark, including during initial preparation or when old segments are rapidly republished. The API lane must gate first delivery on authoritative engine readiness (or return a bounded preparing response), while retaining normal refresh for an already ready runtime. The existing error mapping can return HTTP 503 on the 45-second deadline; UI must visibly show preparing and then failure, respect an explicit user pause, and avoid resetting playback time. No UI/guide/API code was changed here. Client/request timeouts must allow this deadline or use an explicit short polling contract.

**Playback-truth contract still needed:** publisher must atomically associate each advertised sequence/segment URI and PDT interval with actual media ID or slate, fallback reason, and generation; expose current runtime `preparing | playing | fallback | failed`, readiness duration/target, and latest publication time plus segment metadata through the API. Status must describe the segment at the viewer playhead (using its sequence/PDT), not just the latest segment or the guide's wall-clock title. Record fallback when resolution or encoding fails; never infer media identity from the scheduled item alone. This metadata is not implemented in this slice and requires producer/API/UI integration, including restart behavior and safe retention matching playlist URLs.

Before any deployment or channel-setting update, review the gap policy and API gate together; add a real scheduled-media fixture demonstrating exact program identity and frames across a boundary, no unwanted pause/resume or timing reset, bounded failure, and retained active-client URLs. Then use a short controlled Sci-Fi runtime/browser check against the new image, compare actual segment PDT and content with guide, verify source cache status and health, and only afterward consider longer observation. Keep existing cache/free-space limits and leases; do not attribute dropped frames without measurements.

The harness creates red and blue 60-second synthetic H.264/AAC files and a disposable server, media library and SQLite database. It creates a sequential generated channel through the auto-channel API, then stops the server and shifts every generated row and its persisted ownership boundary by the same amount. This controlled fixture age places the existing last row's end near the real current time; it does not change the media, generator definition or continuation cursor. On restart the normal startup renewal appends a new horizon. The test compares every preserved row with its pre-restart copy, verifies the appended first row is contiguous and a different color, and checks both boundary rows against the public guide. It retains both complete row sets. The generated epoch is shifted for the fixture; this does not establish correctness for arbitrary historic epochs or generator configurations.

The capture decodes HLS and `/auto/v99.ts` concurrently at one sample per second and requires the expected marker order. HLS's first new marker must be within 6 seconds of the persisted boundary. Its program-date-time is producer-supplied, and the tolerance allows segment rounding, sampling and producer startup; it is not an independent glass-to-glass clock.

TS is remuxed from HLS by the server, and the harness now embeds a six-bit, one-second source-media timecode in the fixture itself. Before the boundary, it maps decoded timecodes to scheduled media time and records the monotonic receipt of the corresponding TS packet span. It excludes the first three seconds after first-byte startup and the five seconds nearest the boundary from calibration. The measured maximum media age includes producer and transport delay and any schedule-to-media mapping error. It is an empirical bound on sampled frames, not a guarantee about future packets or separate measurements of each queue. One-second source quantization and one-second frame sampling contribute a predeclared 2,000 ms allowance; a conservative 8,000 ms ceiling on the resulting tolerance was fixed before examining the transition. A FIFO actually holds a second copy of each received chunk for 15 seconds; the same transition gate must reject that delayed copy. Startup first-byte time and wall/monotonic pairing uncertainty are recorded separately. The decoded source seconds on each side of the transition are also checked, to catch lost material hidden by a timely color change.

### Private prebuffer follow-up, 2026-11-18

The channel setting is `prebuffer_seconds` (default 8); `initial_burst` is FFmpeg capability detection, not a separate persisted setting. Private readiness uses the legacy `ceil(max(prebuffer_seconds, 0) / clamp(segment_seconds, 2, 10))` segment count, clamped to 1–4. It counts segments already published plus closed segments in the two private generations and a leased segment, and additionally requires a public segment. Startup waits at most 20 seconds and returns an error if the threshold cannot be prepared in time. Segment count is the legacy approximation, not an exact duration guarantee for short segments. Publication still uses scheduled PDT.

Private preparation uses bounded accelerated encoding, independent of FFmpeg's `-readrate_initial_burst` availability. The preparation horizon is one ten-second generation plus `prebuffer_seconds` clamped to 0–10 seconds, and at most two ten-second generations exist; high values therefore saturate the ahead budget rather than allowing unbounded encoding. This is bounded preparation behavior, not an exact reproduction of FFmpeg input read-rate behavior. Negative prebuffer has legacy zero behavior. Focused threshold, bounded-wait, and horizon unit tests passed; they do not prove nondefault real-codec readiness or long-run behavior. After a fresh offline build, the unchanged calibrated capture with prebuffer zero passed: `/tmp/awesome-wave6-prebuffer-final2/ts-timing.json` records source 59 → 0, maximum age 2,981 ms + 2,000 ms allowance = 4,981 ms < 8,000 ms; the delayed FIFO arrived +18,529 ms and was rejected.

# Wave 4: atomic auto-build (slice 7)

Auto-build stages each classic timeline and its continuation before publication. A single SQLite transaction takes the write lock, verifies the existing renewal-input and rebuild-timeline revisions, rechecks channel names and numeric numbers, and writes all channels, classic definitions, timeline items and generated state. The transaction commits before engine refresh, so renewal cannot observe a partial request. Stale inputs or a competing allocation fail the request with a retry message; a fresh request replans against current state. Explicit numbers that have become occupied require a different number. The revision guard intentionally also rejects unrelated concurrent changes to protected inputs or timelines.

Evidence (project root, local real Axum handler and disposable SQLite database):

- Before the change, `timeout 180s cargo test -p awesometv-server auto_build_atomic_failure_retry_and_concurrency -- --nocapture` failed: a trigger aborting the second channel insert left the first channel, items and generated state.
- After the change, `timeout 180s cargo test -p awesometv-server auto_build_ -- --nocapture` passed: 2 tests, 0 failed. SQLite triggers abort the second channel insert and the second channel's timeline insert; each response is an error and snapshots of channels, classic definitions, timeline items, generated state, inputs and revision tables match the initial state. A retry creates the two requested channels. Two simultaneous requests for the same explicit number yield only one success and one persisted channel at that number; retrying the unsuccessful selection at another number succeeds. The test checks four channel definitions, generated states and populated timelines. The existing validation test also passes, including preview/create parity.

The test mounts the actual handler without production authentication middleware. Failure injection covers SQLite insert failures, not process death during commit or a lost HTTP response after a successful commit; requests do not have idempotency keys. This does not prove the Wave 2 privileged CI provisioning gate.

## Integration review and limits

The revision is read before planning/staging; publication obtains the SQLite write lock and compares both revisions before rechecking numeric channel numbers and case-insensitive names. Revision triggers cover channel definitions, collections/media, timeline items and generated state. The classic definition, generated items, fingerprint, boundary and serialized `ClassicCursor` are written in the same transaction. The renewal path reads that fingerprint and cursor and checks generated ownership before extending ([programming.rs](../../crates/awesometv-server/src/programming.rs#L376)); this compatibility is source-reviewed, not a new auto-build-to-worker runtime test.

Engine refresh runs only after commit and returns no error to the handler; it stops existing runners and clears HLS state on a best-effort basis ([engine.rs](../../crates/awesometv-server/src/engine.rs#L190)). Thus refresh cannot cause the handler to report a transaction rollback, but its internal database lookup and filesystem cleanup are not proven successful. A crash, cancellation, or lost response after commit leaves the caller uncertain whether publication succeeded. There is no idempotency key: inspect channels before deciding how to retry; a retry is not guaranteed to reproduce the original success response. The recorded retry test covers a known rollback, not this ambiguous case.

# DNS, TLS and playback assessment — 2026-11-19

## Finding

There is no evidence that the browser resolves DNS for every HLS fragment. The five-second diagnostic probes are separate `curl` processes, so they cannot reuse a previous process's connection or in-process DNS cache, although the OS or resolver may cache answers. Their DNS failures demonstrate trouble on that diagnostic resolution path, not the browser's per-fragment behavior. Browser connection reuse and caching are possible, not guaranteed; reconnection, network changes, expiration, or failures can require new work. The browser's own DNS and connection timing was not captured in enough detail to establish what happened during the stalls.

The [fresh deployment report](fresh-deployment-short-soak-2026-11-19.md) records two recovered stalls and 10 DNS timeouts among 121 public probes. Its private evidence runner `/home/cjrutherford/.t3/soak-evidence/awesome-tv/short-fresh-AZtWetkT/run.py` calls `subprocess.run` for a new curl on each five-second cycle. The separate [pinned comparison report](/home/cjrutherford/.t3/soak-evidence/awesome-tv/pinned-compare-7ZM3w4vC/report.md) reports five normal-path DNS timeouts, but also four pinned-path timeouts and four recovered browser stalls while Chromium used a hostname-to-IP mapping. The latter preserves the HTTPS hostname and certificate verification; it does not establish that DNS caused the stalls or that bypassing DNS cures playback. These are short, separate observations; successful-request percentiles exclude failures.

## Actual delivery path

- `crates/awesometv-server/web/public.html:535` loads hls.js from jsDelivr, a distinct host. `play()` at line 589 loads `/channel/{number}.m3u8` relative to the page origin. The HLS instance is destroyed on channel change, uses prefetch and buffering settings, and restarts loading after fatal network errors; native HLS is a separate fallback. Nothing there explicitly requests a new connection or a DNS lookup per fragment. The channel/guide/config `fetch` calls use `cache: 'no-store'`; that controls HTTP response caching, not a command to close a connection or resolve DNS again.
- `crates/awesometv-server/src/api.rs:2990` reads the producer playlist and prefixes `.ts` lines with the channel number. Normal producer-relative segment names therefore resolve under the same page origin at `/channel/{number}/{file}`; playlist responses use `Cache-Control: no-cache`, segments `max-age=30`. The handlers return bodies rather than redirecting. Other playlist URI forms, proxy redirects, externally supplied streams, and actual deployed responses must be checked in browser network records; source alone cannot rule out a redirect or cross-host request in every deployment. Cast uses a separate path and is outside this finding.
- The observer `tests/e2e/channel-performance/external-soak.cjs:107` performs one Node `dns.lookup` for provenance, and records browser response URLs, peer/security details and failures; it does not record per-request DNS/connect timing or establish every proxy hop. Its local DNS lookup is not necessarily the browser's network path.
- `deploy/nginx/swag/atv.subdomain.conf` describes a separate VPS forwarding to the home host via MagicDNS. Its checked-in upstream already has `keepalive 32`, HTTP/1.1 and an empty Connection header, and TLS terminates at the public nginx. `deploy/nginx/atv.christopherrutherford.net.conf` contains similar settings for a different, local-upstream topology. Repository configuration is not proof of the running forwarding host's configuration or health. The forwarding host and its logs were unavailable in the retained investigation.

## Prioritized actions

1. Capture browser evidence during a reproduced stall: export a bounded Chromium NetLog and collect same-origin Resource Timing entries for playlists and segments with timestamps, DNS start/end, connect start/end, secure-connection start, request/response timing, `nextHopProtocol`, URLs and redirect chains; correlate with player waiting/HLS errors, buffer ahead, failures and server times. Distinguish connection reuse or cache hits from actual DNS work: zero durations alone do not prove a DNS lookup succeeded. Cross-origin timing may be restricted without Timing-Allow-Origin; failed requests and redirects may need NetLog/DevTools evidence. Scrub tokens and URLs before sharing. See [Resource Timing](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming) and [navigation and resource timing](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Navigation_and_resource_timings).
2. Inspect existing time-aligned forwarding-host access/error and upstream timing logs and resolver/network health, plus local origin and producer timing. Verify actual nginx configuration, protocol, upstream address changes, connection reuse and capacity before proposing a change. Persistent upstream connections can reduce connection setup; nginx documents the relevant [upstream keepalive and DNS resolution options](https://nginx.org/en/docs/http/ngx_http_upstream_module.html). A server-side upstream hostname may be resolved and cached or pinned according to nginx version and configuration, with refresh/failover implications; preserve the correct HTTP Host and, for HTTPS upstreams, TLS SNI and certificate verification. The checked-in SWAG upstream is HTTP, so upstream TLS SNI does not apply to that hop. Do not assume the checked-in file is deployed or prescribe a speculative edit.
3. Diagnose resolver reliability on the affected client/network when new browser connections actually need resolution. Retain the verified HTTPS hostname and normal certificate validation. A controlled `curl --resolve` or browser host-resolver mapping is a diagnostic comparison, not a production URL rewrite or global hardcoded IP. Browser JavaScript cannot arbitrarily set `Host` or `Connection` ([forbidden headers](https://developer.mozilla.org/en-US/docs/Glossary/Forbidden_request_header)); an HTTPS IP URL normally requires a certificate valid for that IP and does not preserve hostname-based SNI/routing. [curl's name resolution guidance](https://everything.curl.dev/usingcurl/connections/name.html) explains hostname-preserving `--resolve`.
4. Preconnect is at most an optional initial-connection optimization for a genuinely separate origin; it cannot ensure reuse or cure recurring stalls. The page already connects to its own origin, and already preconnects to font hosts. No new player preconnect or retry change is justified by the evidence.

For any eventual targeted change, compare before/after stall count and duration, buffer ahead, playlist/segment failure and latency, browser DNS/connect/TLS and reuse, plus forwarding-host request/upstream timing and resolver errors under comparable conditions. Check successful playback and certificate/hostname validation, recovery after disconnect and address changes, and rollback. This assessment makes no app or production configuration change and does not claim a playback fix.

# Producer repair patch 2: incomplete private publisher groundwork

Wave 6 is **not accepted**. The public producer and lifecycle remain unchanged. This patch does not yet provide the requested private vertical slice and must not be wired into production.

`engine/private_publisher.rs` contains an isolated playlist parser and publisher prototype. It parses decimal EXTINF into 90 kHz ticks, restricts private segment names, gates publication on the scheduled end, checks item start against the accumulated cursor, copies segments to unique public names, atomically replaces the playlist, and advances sequence and discontinuity sequence as entries leave the playlist. Publication failures retain the previous snapshot and cursor. It does **not** delete aged-out files.

Focused verification: `timeout 90s cargo test --offline -p awesometv-server engine::private_publisher::tests`. The FFmpeg test generates four different solid-color 1.2-second items, each with three private HLS segments including a partial final segment, and publishes them through three item boundaries. It checks segment durations, entry count, media sequence and discontinuity sequence. Other tests check decimal rounding, pacing, invalid input and snapshot preservation on error. This is a real FFmpeg muxer/playlist integration check, not a source-timecode or TS playback continuity test. It does not exercise concurrent publication or atomicity under readers.

## Remaining before the requested patch is complete

- Implement `start_private_item(channel, item, seek_ms, remaining_ms, private_dir) -> Result<Child>` using the existing mappings, filters and codec settings; ensure it can only write a unique private generation. Add slate support.
- Implement a cancellation-safe bounded current/next spool controller, pausing and resuming process groups, reaping children and removing private generations. Establish hard bounds including encoder overshoot, and stall on failure, missing segments, malformed playlists and non-seekable inputs.
- Connect the controller to a publisher that consumes only playlist-referenced complete segments in schedule order. Persist explicit item start/end and original `in_ms`, validate total item duration within frame/audio tolerance, and retain unlisted public segments for cache lifetime plus advertised playlist duration. Implement safe cleanup, backpressure and stall diagnostics/recovery.
- Extend the actual FFmpeg test to encode distinct source timecodes across at least three boundaries, decode every tail/head, assert schedule-derived PDT and sequence, measure queue/pacing bounds and exercise cleanup, failures and cancellation. Reuse the binary marker instrumentation in `tests/e2e/stream_agreement.py`.

The eventual production switch should feed the private controller the initially trimmed item and persisted adjacent schedule rows, and call a single publisher with closed segment paths, full-precision durations, explicit scheduled item starts and a wall-clock value. The present `Publisher::publish` is only a candidate for that internal interface; lifecycle ownership, readiness, health and cancellation are not implemented. Patch 3 must not start until the missing patch 2 checks pass. TS remux and the existing calibrated Wave 6 gate remain untested here.

## Subsequent bounded lifecycle slice (still incomplete)

The disconnected prototype now has `PrivateSpool::new(root)`, `start(command, segment_seconds)`, and `finish_current()`: at most two direct FFmpeg children can be owned, each uses a UUID generation and private HLS output; `finish_current` waits for success, requires ENDLIST and existing playlist-referenced segment files, and transfers the generation directory to the caller for removal. Dropping the spool kills and waits for its remaining direct children and removes their directories. The existing four-item FFmpeg test now uses this interface. `Publisher::cleanup(now_ms)` removes retired publisher-owned segments after 30 seconds plus the playlist duration at retirement, leaving advertised entries alone. The cleanup is not yet protected against in-flight reads.

Verification: `timeout 90s cargo test --offline -p awesometv-server engine::private_publisher::tests` passed 4 tests on Linux, including real FFmpeg at three boundaries, a two-child queue rejection and drop/reaping check, and retention deadline checks. The boundary test still checks durations and order, not decoded source timecodes. The child test checks direct child PIDs, not process groups.

This is not a bounded production spool: queue length is bounded but disk use, encoding lead and process descendants are not; no pause/resume or asynchronous cancellation exists. `finish_current` blocks until an entire item has encoded, and callers must clean transferred directories. There is no production command builder, slate support, source-timecode continuity test, item duration validation, streaming consumption, or live wiring. Do not integrate this interface into the public producer until those gaps and safe in-flight segment reads are addressed. No latency, TS continuity, or Wave 6 acceptance is claimed.

## Follow-up safeguards (private prototype only)

The preceding paragraph describes the earlier revision. The prototype now rejects requested generation durations outside 1–10,000 ms and adds an output `-t`; two generations can still run ahead independently, so this is not the design's publication-relative lead control. It still accepts an arbitrary command and does not enforce a byte budget. Longer items need a segment-ready incremental controller, with quota-enforced storage or a capped output pipe, bounded segment overshoot, and backpressure; splitting independent encoders at arbitrary ten-second points alone risks losing frames and timestamp continuity. Those mechanisms are not implemented here.

Completed generations own and remove their directories on drop. On Unix each child starts a process group and cancellation sends SIGKILL to that group before waiting for the direct child; other platforms fall back to killing and waiting for the direct child only. Descendants are not reaped by this process, and descendants that escape the group are outside this protection. The Linux test verifies a descendant is no longer running, including the possible zombie state, not that an unrelated init has reaped it. Blocking `finish_current` still needs an asynchronous cancellation owner.

The real FFmpeg frame test compares decoded, losslessly encoded source frames immediately before and after three one-second item boundaries, and verifies all 20 source frames are distinct. It is not a production codec, audio, remux, or live timing proof. The existing retention deadline is 30 seconds plus the advertised playlist duration, matching the current segment route's 30-second cache header, but cannot guarantee an in-flight read that starts just before expiry. The production route must acquire a read lease before resolving the path and release it after reading, or use another proven coordination mechanism; the prototype has no route integration.

Before any production switch: enforce spool bytes and publication-relative lead with incremental segment consumption and cancellation-safe backpressure; build typed private commands from the production media and slate mappings; validate source seekability, durations and schedule adjacency; coordinate leases with segment routes; implement lifecycle, readiness, stall/recovery and cleanup; prove actual codecs, audio and TS remux across boundaries and run the calibrated external capture. Wave 6 remains unaccepted until that later external capture.

Verification on Linux: `timeout 90s cargo test --offline -p awesometv-server engine::private_publisher::tests` passed 8 tests, including the decoded-frame and process-group tests. No public lifecycle was changed.

### Incremental private segment polling

The prototype now offers `take_ready_segment` on the oldest generation: `Pending` means poll again, `Segment` transfers the next completed segment into a lease, and `End` marks a successfully exited generation with a complete playlist (or an empty queue). The caller may poll again for a queued next generation. The method validates consecutive segment names, advances only after a successful transfer, and reports encoder and playlist errors. It cannot be mixed with `finish_current` after taking a segment. FFmpeg's existing `temp_file` HLS flag closes and renames segment files and playlist snapshots before they are observed; no encoder completion wait is used for a take.

Evidence: `cargo test -p awesometv-server incremental_ --offline` passed both tests with real FFmpeg 8.0.1. A paced eight-second lossless fixture demonstrated that the child was still running at the first take, and all eight decoded segments reproduced the 40 distinct source frames in order, including the first and last frames. A second paced child was cancelled after a partial take; it was reaped, its generation directory removed, and the lease remained decodable until dropped. Separate checks cover encoder failure and a successful exit without `ENDLIST`.

This supersedes the earlier statements that incremental consumption is absent. It remains a private prototype, with at most two finite-duration children; it does not enforce an aggregate byte cap, publication-relative lead, or backpressure. Production command construction, route integration, pause/resume, audio and production-codec continuity remain unproven.

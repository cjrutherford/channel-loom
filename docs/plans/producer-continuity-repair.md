# Producer continuity repair

## Evidence and decision

`engine.rs::ensure_inner` selects `current_item(now)`, kills the previous `Runner.child` when its key changes, and starts a writer to the same `index.m3u8`; the supervisor calls it every two seconds. `trim_window` seeks from wall time. Thus an encoder behind wall time loses its unpublished tail and a late next launch seeks past its head. `start_producer` numbers PTS using segment count times nominal duration, not actual durations. `api.rs::hls_playlist` serves that file, `hls_segment` reads its named files, and `ts_stream` starts a separate FFmpeg HLS-to-TS remuxer per client. Changing only the playlist is insufficient if the source process is killed.

The rejected `/tmp/awesome-slice12-rejected-candidate.patch` drains then uses FFmpeg `append_list` with start number zero. It preserved sampled tail/head but measured 9,085 ms calibration tolerance, and another run produced a new program date before the old tail; draining serially can add delay every boundary. Baseline lost seconds 54–59, with tolerance 9,262 ms. See `docs/reviews/wave-6-stream-agreement.md`. No continuity or latency acceptance has been established.

Choose **one Rust-owned paced publisher per channel, with private per-item FFmpeg encoders prepared ahead**. The publisher alone writes the public playlist and owns sequence, dates, retention and child lifetimes. Private encoders never touch public files. This preserves existing media filters, per-item input selection, HLS routes and client remuxing. A single concat FFmpeg would need dynamic inputs, stream normalization and reconnect handling; serial drain/append retains the measured latency accumulation and FFmpeg date ownership. Prefetch consumes bounded extra CPU/disk; if throughput is insufficient the design reports failure rather than silently dropping content or promising a latency bound.

## Contract and mechanics

In `crates/awesometv-server/src/engine.rs`, replace per-item `Runner` with a channel task and handle: `Runner { cancel, join, playlist, last_access_ms, ... }`. `ensure_inner(&self, channel: &Channel) -> Result<PathBuf>` starts it once, awaits readiness without holding the global runners mutex, and only updates access; `refresh`, idle stop and `stop_all` cancel and join it. Task states: `Starting -> Running -> Stalled -> Running`, or `Stopping -> Stopped`; one task serializes all transitions. Startup selects the current item at now and `trim_window` once. Thereafter walk persisted adjacent schedule rows by end/start, using next `in_ms` exactly, never reselect by wall clock. Gaps use a bounded slate item; edits invalidate only uncommitted future work, never already published entries. Re-resolve before launching each future item.

Refactor `start_producer`/`start_slate_producer` into `start_private_item(channel, item, seek_ms, remaining_ms, private_dir) -> Result<Child>` while retaining current maps, filters, codecs and keyframes. Remove input `-re`/read-rate burst for these workers; retain `-ss` and output `-t` for the exact item interval. Use `-f hls -hls_time S -hls_list_size 0 -hls_flags temp_file+independent_segments -hls_segment_filename PRIVATE/seg_%09d.ts PRIVATE/index.m3u8`; no append, delete, `program_date_time`, `discont_start`, `start_number` offset, or public `-output_ts_offset`. Use unique generation directories. A closed segment is eligible only after its private playlist references it; parse EXTINF at full precision. FFmpeg exit success and the final playlist establish end-of-item. No concurrent writer may touch a generation.

Prepare current and at most one next item, starting the latter when current remaining scheduled time is <= max(2*S, 10s); each private spool may run ahead at most `max(2*S, 10s)` of published media. Stop reading/launching work when full: suspend/resume the child process group with a cancellation-safe guard, or implement an equivalent bounded producer pipe; never block while holding the runners mutex. Resume before the spool empties. Reject a non-seekable source that cannot be safely throttled; expose stall rather than unbounded disk. On cancellation always resume any stopped group, terminate, wait/reap, and delete only private files. A child failure, missing segment, malformed playlist, disk-full, or no ready successor enters `Stalled`, retains last good public playlist, logs item/error, retries with bounded backoff and exposes unhealthy status; do not skip ahead or emit fake success. Recovery must resume the exact unpublished source offset or restart a private generation and discard already published media; if exact resumption cannot be established, stop and require explicit discontinuous restart. No continuity guarantee across an actual unrecoverable source error.

`publish_ready(&mut Publisher, now: i64) -> Result<()>`: maintain integer 90 kHz `cursor`, anchored once at the first selected schedule instant, and entries `(seq, path, duration_ticks, date_ticks, discontinuity)`. Read each private segment's actual packet/EXTINF duration in ticks, verify it is positive and within a frame/audio-packet rounding tolerance of its scheduled interval. Publish in item order only once its scheduled end is <= now; do not sleep on old child exit after final segment is complete. Atomically rename/copy the completed segment into public storage with a globally unique name, then atomically replace the playlist via same-directory temp+rename. Set each `PROGRAM-DATE-TIME = anchor_utc + cursor/90000`, advance cursor by actual duration, and place `EXT-X-DISCONTINUITY` at every item change; never derive dates from FFmpeg process start or `sequence*S`. At a boundary compare cursor to the next row's scheduled start: compensate only representable sub-frame rounding by choosing the nearest tick boundary, and otherwise stall with diagnostics rather than let drift accumulate or move dates backward. Format dates with sufficient fractional precision; ensure next date >= previous date + previous EXTINF after rounding. Encode/mux timestamps may reset per item; discontinuity communicates this to HLS clients. Validate actual TS remux behavior before claiming continuity; do not claim globally monotonic MPEG PTS from playlist dates.

Keep the latest `cache_segments.clamp(4,60)` entries in the public playlist with monotonic media sequence and correct discontinuity sequence when entries age out. Keep unlisted files for at least the existing 30-second segment cache lifetime plus one full advertised playlist duration, then unlink; never clear an active directory on transition. Bounded cache and two bounded private spools cap storage; slow clients can still fall behind retention. Public segment names remain immutable; HLS and cast route rewrites and `auto` remuxer need no interface change. Shutdown removes children and private generations, not still-advertised public bytes; restart uses a fresh generation and explicitly signals discontinuity. Disk cleanup must not race an in-flight segment read.

## Feasibility and patches

The existing gate is max sampled age + 2 s <= 8 s, so sampled age must be <= 6 s. Harness configuration is S=2 s, prebuffer=0, cache=30: 30 is retention, not necessarily 60 s of latency. A player/remuxer starting three segments behind already consumes about 6 s, leaving no budget for encoding, delivery or the allowance; feasibility depends on actual FFmpeg client live-edge selection and measured delays. Default S=4, prebuffer=8 cannot mathematically meet this gate if that full eight seconds lies on the measured path. No universal 8 s guarantee follows from configuration, nor should the assertion be relaxed. Measure and, if necessary, explicitly configure the TS remuxer's HLS live-edge behavior while preserving the entire boundary; an 8 s result remains an empirical gate, not an SLA.

1. **Independent diagnostic patch:** in `engine.rs` add structured timestamps/counters for child spawn/exit/kill, segment availability, playlist replacement and scheduled item boundaries; in `tests/e2e/stream_agreement.py` retain per-segment EXTINF/PDT and TS receipt trace. No lifecycle change. Acceptance: focused unit test for timestamp/entry parsing plus one existing isolated capture that still fails the unchanged continuity gate but identifies old producer kill and segment publication times. Run `cargo test --offline -p awesometv-server <focused-test>`; build offline then run the documented `STREAM_EVIDENCE_DIR=... timeout 180s python3 -u tests/e2e/stream_agreement.py`. A failure is expected and its artifact must show why.
2. Add private spool and single publisher with deterministic tests for atomic playlist snapshots, sequence/retention/discontinuity, timestamp rounding, bounded queues, cancellation/reaping and failure; exercise actual FFmpeg with short adjacent fixtures, including different streams and partial last segment. No public switch until these pass.
3. Wire channel lifecycle and routes to publisher, test concurrent ensure/refresh/idle and stale segment reads; run existing isolated capture unchanged, including delayed FIFO control. Extend with several adjacent items and source timecodes: assert every tail/head, nondecreasing end-to-start PDT, bounded age without cumulative drift, no replay, and TS playback through all boundaries. Capture queue depth and worker times. Run one focused server test and one bounded isolated integration run after build; retain logs and report actual gate values. Test failure recovery separately before claiming it works.

Isolate TS startup buffering, then prove the wired ten-second generations and unsupported-source handoff with decoded audio/video across at least three boundaries, monotonic playlist sequence/PDT, bounded age and backlog, and FIFO negative control. Integrate observability/lag handling only without chopping queued tail; document or implement prebuffer/initial-burst compatibility. See `docs/reviews/wave-6-stream-agreement.md`.
